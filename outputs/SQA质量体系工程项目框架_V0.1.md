## 1. 建设目标与范围

- **团队质量看板**汇总各项目、版本和阶段的达标情况、证据覆盖、未决风险及到期行动。项目成员能填报和提交证据，项目 SQA 能复核，管理者能下钻至获授权的明细。
- **过程 PR 审计和 Bug 审计**复用现行工具及已批准口径。TP需求、TP缺陷（TP/TAPD）、Bitbucket PR、TeamCity 和 CI/CD 继续承担原业务记录与操作。平台管理跨系统索引、快照、审计结论与整改证据。
- **质量回溯看板和质量文化期刊**从已复核的问题或优秀实践出发，支持 RCA、CAPA、复发跟踪、案例脱敏发布及标准修订。
- 首轮范围已确认，交付项目与指标、PR / Bug 文件导入、整改与验证。质量回溯、文化期刊和只读 API 同步进入后续阶段，API 同步以授权与实测为准。原系统自动写回、自动放行、自动红线定性或绩效联动均不列入建设范围。

## 3. 业务闭环与判定口径

**原始证据 → 规则检查 → SQA 人工复核 → 风险或不符合项 → Owner 整改 → 独立验证或 CAPA → 案例沉淀 → 标准修订。**

- **录入与复核。** 每个发现回链原始批次、记录与规则版本。匹配歧义、缺证和规则冲突进入待复核队列。确认不符合前核查适用条款、证据和已批准例外。红线事件和绩效事项遵循各自批准流程。
- **行动与关闭。** 记录风险等级、影响范围、责任人、截止日、完成证据、验证人及升级对象。状态依次为待复核、已确认、整改中、待验证、已关闭，支持退回、升级和复发重开。延期、豁免与接受剩余风险保留审批和到期日。整改提交和验证关闭为两个动作。
- **回溯与改进。** 对重大、重复或疑似系统性失效按有效规则触发复盘。记录影响和时间线、临时遏制、根因、纠正及防复发措施，事先约定观察窗口、样本与效果标准。效果验证失败则重开或升级。案例可提出标准修订，获批后建立新版本和生效范围。
- **看板灯色。** 依据已批准目标和相同项目、版本、阶段的有效证据生成红、黄、绿。缺证、分母为零、口径未确认或数据过期时显示待补证或待确认，综合视图保留未评估覆盖及关键阻断项。批准不适用应可追溯，关键门禁缺证不得判绿。自动化和软测负责建设与执行冒烟，SQA 监督、复核证据和推动升级。TeamCity 构建成功与冒烟业务结论分别记录。
- **PR 口径。** 先确认 Release Note 条目与仓库 PR 的匹配，再复核 TP 追溯、目标分支、评审批准、评论或任务关闭、自测、构建和风格检查。分别统计 Release 条目与唯一 PR。历史 CI 失败仅作为线索，合入判断核对相应提交与合入时间线。历史审计记录保留原结论，高风险和疑似红线项需人工确认。
- **Bug 口径。** Race 3 / Race 3S 历史基线按 Driver、Framework、UI 三团队和 Blocking、Critical、Major、Normal 四级筛选，按 Bug ID 去重、使用 `Entity State`，排除 `Invalid`、`Wont fix`、`Duplicate`。研发待解决为 New + In Progress + In Review，另列待验证与待复现。管理关闭率 = 1 − 研发待解决 / 有效缺陷。周报验证完成率 =（Verified + Fixed）/ 有效缺陷，统计注明状态口径。单条风险的实际验证关闭须核验验证证据。同一 Bug ID 两个快照可核对状态迁移，池净变化只反映汇总差异。跨项目使用阈值或口径前需确认基线。

## 6. 架构建议与本机试点

建议采用 **浏览器 Web + 后端服务 + 关系数据库 + 受控证据文件存储**。后端处理权限、计算与审核流程。复用现有 Python 数据处理和 JS 看板逻辑中可独立验证的部分。定时任务可承担导入队列、数据新鲜度提示和备份。TP/TAPD、Bitbucket、TeamCity 的只读连接器留到授权验证后启用。具体技术栈随使用规模、组织运维能力与 IT 支持确定。单人原型可评估 SQLite，团队并发优先评估 PostgreSQL，并验证企业现成数据库方案的可维护性。

| 部署阶段 | 条件和验证 |
| --- | --- |
| 本机验证 | Windows 用户本机仅绑定回环地址，验证文件导入、规则、审批和恢复。运行数据与历史源分开，应用凭证存服务端受控配置，前端和日志不得写入凭证。 |
| 局域网团队试点 | 采用 IT 已分配的内网域名与 HTTPS 证书，沿用现有网络策略，无需新增访问端口或修改防火墙规则。上线前从办公网设备验证域名解析、证书信任和实际访问范围，落实账户停用和权限回收。禁止未经授权的公网访问与内网穿透。 |
| 可运营性 | 约定试点服务时段，评估休眠、断网、重启与补丁影响，采用经批准的自启方式。备份覆盖数据库、证据文件及必要配置，备份权限与生产权限分别管理。用隔离环境恢复并核对记录数、权限、证据链接与审批历史，按确认的恢复目标计时。若本机可用性无法满足团队试点，再评估 IT 托管环境。 |

## 7. 数据治理、导入与迁移

1. **先保全。** 从原使用者原浏览器、配置和打开入口导出全量 JSON。多人或多浏览器分别导出，记录导出时间和持有人，保存受控原件并生成 SHA-256。同步封存发布 HTML、种子数据、历史工作簿、PR 和 Bug 原始文件。导出缺失时，相关浏览器实绩标为待迁移。
2. **先试导再发布。** 批次记录项目范围、来源类型、文件哈希、快照截止时间与时区、格式和映射版本。暂存区检查必填字段、外部 ID、重复、范围错配、版本别名和未知状态，出具异常清单供复核。批准后原子发布，重复提交同一批次复用结果，失败重试不得产生半批数据。规则重跑或运营纠错以新结果版本保留原记录和原因。
3. **校对与冲突处理。** 逐来源对账项目数、唯一指标数、目标变体、阶段、里程碑和实绩快照；抽查档案与原看板的证据链接和灯色。对 PR 检查 Release 和仓库去重，Bug 检查 ID 覆盖、状态和时间边界。不同人导出产生的同键冲突先进入异常队列，由指定 Owner 签认。迁移前确认回退点，验证批次撤回后旧基线可恢复。
4. **按敏感度保存。** 原文件、快照、规则与审批版本可追溯，证据和访问日志按 IT 确认的期限保留。跨团队原始日志、客户数据和代码留在获准环境，平台优先保存授权引用和必要摘要，禁止上传公开服务。文化案例发布前移除客户、个人、代码、内部地址及可重识别信息，并复核目标受众可见范围。
5. **只读同步准入。** 针对每个来源确认批准主体、账号范围、字段覆盖、速率限制与访问审计。用文件基线验证 API 记录和时间戳、增量游标、失败重试、删除或改名处理及授权撤销。连接状态当前为待验证，受控文件导入是首期稳定入口。

## 11. 首轮实施细化

### 实施方案与顺序

1. **先定数据契约和验收样本。** 在本地隔离环境使用获准的历史资料，登记来源、SHA-256、取数范围、截止时间、记录定位及映射版本。原始文件以只读方式取证，暂存、发布和回退可独立核查。
2. **构建本机 MVP。** 建议采用 Python Web 服务、复用现有 HTML/JS 中可验证的界面与逻辑、SQLite 本机数据库和受控证据目录。Flask + Waitress 可作为 Windows 回环部署候选，实施时先验证现有环境和依赖来源。发布业务记录使用数据库事务，技术框架或数据库变更保留稳定的业务标识和迁移脚本。[Flask 的 Waitress 部署文档](https://flask.palletsprojects.com/en/stable/deploying/waitress/) · [SQLite 适用场景](https://www.sqlite.org/whentouse.html)
3. **完成本机验收再准备团队开放。** 团队阶段优先评估 PostgreSQL 或现有 IT 批准的数据库。用实际办公网入口验证并发读写、重启恢复和证据访问，完成 P2 数据迁移及恢复演练后再开放。技术栈建议依据实施验证定稿。[PostgreSQL 并发控制说明](https://www.postgresql.org/docs/current/mvcc-intro.html)

### 验收职责与上线检查

- **本机验收由业务 Owner 组织，肖强协同审核。** 提交导入对账表、异常清单及整改验证记录。走查一次同一账号提交整改后尝试自验、关键证据缺失和异常导入回退。演练记录标记用途，正式历史结论沿用原证据和审批。
- **团队开放由运维 Owner 核验，IT 协助现有网络入口。** 在办公网另一台设备验证 HTTPS 信任和实际可达性，验证 10 个账号和三类角色，检查项目、附件和导出权限。复核停用后已有会话权限、重启、工作日备份和 4 小时恢复演练结果。运维记录最近成功备份及失败原因。主机和本地备份同时不可读取时，恢复依赖另有可用副本。
- **上线后按试点周期回看。** 统计导入对账结果、待复核积压、行动逾期和可用性。记录实际容量和响应情况后再设运营指标；版本实绩或正式签核取得后追加取证记录。
